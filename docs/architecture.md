# Lexcia architecture

The website calls its own Lexcia backend on port 8767. Each request carries the browser conversation UUID. The backend validates requests with Pydantic, ranks local knowledge with BM25, runs a retrieve → answer LangGraph, and translates model chunks into SSE status/item/delta/final events. The scoped prompt answers only from reviewed Lexcia information. No ArchiveLens imports, process, corpus, configuration, or server calls are required.

Sessions are isolated in memory, limited to 128 idle/active entries and ten completed turns per session. Restarting the backend loses its conversation context; on Vercel, a new function instance may also start without earlier turns. Browser transcripts remain local; only the active conversation is exposed in the website UI. Only completed turns enter backend history. Concurrent requests in the same session are rejected, and cancellation releases its lock. There is no account system or durable server history.

The existing launcher, modal, pinning, resizing, keyboard navigation, saved browser transcripts, and React generative-UI renderer are adapted from the prior local demo. The floating panel anchors to the draggable launcher using viewport-constrained placement that prefers the launcher below the panel’s bottom-left corner; it recalculates on opening, size changes, viewport changes, and unpinning. Pinned mode docks on the right with page space reserved beside it. It uses native `dialog.show()` rather than `showModal()`, so the page remains interactive without a backdrop or click-outside dismissal. Unpinning restores the floating modal; closing removes the reserved page space. The divider measures pointer position from the right, with ArrowLeft increasing width and ArrowRight decreasing it. Page container queries keep headings and grids readable as sidebar width changes. Desktop arrival opens this pinned sidebar once after about one second, preserving page keyboard focus; user-initiated opening/closing cancels that scheduled opening, and widths at or below 700 px keep the manual launcher. Rich response rendering is available in the frontend but this backend currently produces sourced text only. Source metadata identifies the project's reviewed knowledge records; the Sources footer is currently hidden. Product positioning, branding and planned pricing are traceable to the reviewed Google Drive document, while implemented demo behavior is traceable to the local prototype. Unknown commercial details are explicitly recorded.

ArchiveLens informed the separation of knowledge, prompts, retrieval, graph, streaming, and UI. Sefaria and assistant-ui remain design references. The backend is a new implementation.

Conversation messages follow the layout and action-bar patterns in [assistant-ui's thread component](https://github.com/assistant-ui/assistant-ui/blob/main/packages/ui/src/components/react/assistant-ui/elements/thread.aui.tsx), using the existing DOM/SSE conversation controller. User messages are compact right-aligned bubbles; assistant replies render Markdown with inline code and copyable code blocks. Answers provide copy and helpful/unhelpful controls. Thumbs-down opens a keyboard-accessible dialog with a reason and optional note; cancelling preserves the previous rating, and saved negative feedback can be edited or removed. Feedback stays in local browser transcripts, with no backend submission or training integration. Copying removes internal source markers. The welcome screen now adapts the actual website’s `AssistantWelcome` from [its source thread](https://github.com/assistant-ui/assistant-ui/blob/main/apps/docs/components/pages/docs/assistant/thread.tsx), with the license notice distributed at `/licenses/assistant-ui.txt`. `thread-welcome.jsx` mounts `AssistantRuntimeProvider` and `ThreadPrimitive.Root`, uses `AuiIf` for empty-thread content, and sends questions through `ThreadPrimitive.Suggestion send`. An external-store runtime reflects the active transcript and running state, and forwards new messages to the existing submit function. The app remains the source of truth; this first integration step covers the greeting and starter suggestions, with message bodies and the composer still rendered by the existing controller. The greeting and starter rows use staggered entrance motion, disabled under reduced-motion preferences, and the website’s subtle row/text/arrow hover treatment in Lexcia colors. A waiting indicator covers the first streamed text inside the answer; the composer has no duplicate progress text, grows with drafts, and adjusts to width changes. A jump-to-latest control appears when the reader scrolls away from the bottom. Message timestamps, calendar-day dividers and the separate Sources footer are currently omitted from the website chat, including saved conversations. The saved timestamp/source data and backend grounding are retained. Rich response rendering and existing frame controls retain their prior behavior.

Stopping a response saves its partial text and sources, with a Continue action on the latest turn of the active conversation. Continue appends streamed text to the same assistant message without adding another user bubble. It uses the original question plus the ending of the saved answer in a bounded request (at most 4,000 Unicode code points, matching the chat API); long questions and answers use excerpts. This is a new model request with context, not a paused provider stream. Failed continuations retain the partial answer and offer another attempt. New inquiries immediately get fresh session UUIDs rather than waiting for a reset request; previous browser transcript data is retained internally. The website no longer exposes a history list or read-only history view; the + button starts a new chat immediately.
