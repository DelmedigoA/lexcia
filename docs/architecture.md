# Lexcia architecture

The website calls its own Lexcia backend on port 8767. Each request carries the browser conversation UUID. The backend validates requests with Pydantic, ranks local knowledge with BM25, runs a relevance guard → retrieve → answer LangGraph, and translates model chunks into SSE status/item/delta/final events. The scoped prompt answers only from reviewed Lexcia information. No ArchiveLens imports, process, corpus, configuration, or server calls are required.

Sessions are isolated in memory, limited to 128 idle/active entries and ten completed turns per session. Restarting the backend loses its conversation context; on Vercel, a new function instance may also start without earlier turns. Browser transcripts remain local; only the active conversation is exposed in the website UI. Only completed turns enter backend history. Concurrent requests in the same session are rejected, and cancellation releases its lock. There is no account system or durable server history.

The existing launcher, modal, pinning, resizing, keyboard navigation, in-memory transcripts, and React generative-UI renderer are adapted from the prior local demo. The floating panel anchors to the draggable launcher using viewport-constrained placement that prefers the launcher below the panel’s bottom-left corner; it recalculates on opening, size changes, viewport changes, and unpinning. Desktop right-side launchers fit floating height to the space above them (minimum 360 px) to retain the reference opening on shorter viewports. Layout preferences last only for the current visit. Pinned mode docks on the right with page space reserved beside it. It uses native `dialog.show()` rather than `showModal()`, so the page remains interactive without a backdrop or click-outside dismissal. Unpinning restores the floating modal; closing removes the reserved page space. Pinning and unpinning preserve the current conversation and do not replay the panel entrance or welcome animations, including while an answer is running. The divider measures pointer position from the right, with ArrowLeft increasing width and ArrowRight decreasing it. Page container queries keep headings and grids readable as sidebar width changes. The launcher defaults to 69.4% of viewport width and 73% of viewport height, clamped within the viewport. Mobile page loads open the floating assistant after half a second; desktop starts with the same single dialog embedded in the hero. Closing desktop floating/pinned chat returns that instance to the hero, preserving the transcript and mounted React state. The old animated hero chat is removed. The launcher hides while the hero is in view or the sidebar is pinned. Manual opening cancels the pending timer, preventing reopening after dismissal; users can also open through chat buttons or sample questions. Rich response rendering is available in the frontend but this backend currently produces sourced text only. Source metadata identifies the project's reviewed knowledge records; the Sources footer is currently hidden. The active corpus has seven short records mapped to the landing-page sections. Answers give a brief explanation with a relevant natural section link when useful; follow-up buttons provide the learning/demo actions. Pricing includes reviewed approximate USD setup/subscription ranges, separate API usage and early-organization terms, linked to #demo. Internal architecture and old demo behavior remain outside the current knowledge scope. Desktop section links pin the assistant on the right at 30% of viewport width before navigating and focusing the destination. Mobile closes the floating modal before jumping. The divider remains resizable, with width tracked as a viewport ratio. Starting demo scheduling also pins the desktop assistant at 30% width (preserving a manually wider sidebar) and opens the local scheduling preview. `knowledge/system.md` defines scope and `knowledge/instructions.md` defines brief answers and progression toward a demo through the follow-up suggestions; both are combined in the model system context.

ArchiveLens informed the separation of knowledge, prompts, retrieval, graph, streaming, and UI. Sefaria and assistant-ui remain design references. The backend is a new implementation.

Conversation messages follow the layout and action-bar patterns in [assistant-ui's thread component](https://github.com/assistant-ui/assistant-ui/blob/main/packages/ui/src/components/react/assistant-ui/elements/thread.aui.tsx), using the existing DOM/SSE conversation controller. User messages are compact right-aligned bubbles; assistant replies render Markdown with inline code and copyable code blocks. Answers provide copy and helpful/unhelpful controls. Thumbs-down opens a keyboard-accessible dialog with a reason and optional note; cancelling preserves the previous rating, and saved negative feedback can be edited or removed. Feedback stays in page memory, with no backend submission or training integration. Copying removes internal source markers. The welcome screen now adapts the actual website’s `AssistantWelcome` from [its source thread](https://github.com/assistant-ui/assistant-ui/blob/main/apps/docs/components/pages/docs/assistant/thread.tsx), with the license notice distributed at `/licenses/assistant-ui.txt`. `thread-welcome.jsx` mounts `AssistantRuntimeProvider` and `ThreadPrimitive.Root`, uses `AuiIf` for empty-thread content, and sends questions through `ThreadPrimitive.Suggestion send`. An external-store runtime reflects the active transcript and running state, and forwards new messages to the existing submit function. The app remains the source of truth; this first integration step covers the greeting and starter suggestions, with message bodies and the composer still rendered by the existing controller. The greeting and starter rows use staggered entrance motion, disabled under reduced-motion preferences, and the website’s subtle row/text/arrow hover treatment in Lexcia colors. A React-mounted waiting line adapts the website’s `TraceLine` and `ShimmerLabel`: a quiet > marker and an ochre/ink shimmer over “thinking…” (or “continuing…”). Its root is unmounted before streamed prose replaces it and on all completion/error/cancel paths. Reduced-motion and forced-color modes use a static, readable label. Backend status messages do not replace the label. This indicator covers the wait for the first streamed text inside the answer; the composer has no duplicate progress text, grows with drafts, and adjusts to width changes. A jump-to-latest control appears when the reader scrolls away from the bottom. Message timestamps, calendar-day dividers and the separate Sources footer are currently omitted from the website chat, including saved conversations. The saved timestamp/source data and backend grounding are retained. Rich response rendering and existing frame controls retain their prior behavior.

The composer has no Stop button; Send stays visible and disabled while a response runs. Previously stopped or interrupted saved responses retain their recovery path, with a Continue action on the latest turn of the active conversation. Continue appends streamed text to the same assistant message without adding another user bubble. It uses the original question plus the ending of the saved answer in a bounded request (at most 4,000 Unicode code points, matching the chat API); long questions and answers use excerpts. This is a new model request with context, not a paused provider stream. Failed continuations retain the partial answer and offer another attempt. New inquiries immediately get fresh session UUIDs rather than waiting for a reset request; a reload starts with no previous transcript. The website no longer exposes a history list or read-only history view; the + button starts a new chat immediately.

Demo scheduling is a client-only React card in the existing transcript. Explicit scheduling requests and the header/contact buttons create a completed local turn with form state, bypassing the model API. A reservation-style form validates preferred future local dates/times and contact details; review shows an event summary and semantic details table. Editing retains inputs, discarding clears them, and React roots are unmounted when changing inquiries. No scheduling API, availability lookup, invitation or calendar integration is implemented.

Section links render inline in bold with an underline. A Markdown token pass styles section links while preserving the model’s natural wording. The current destinations are #home, #why, #look and #demo. Product overview links target Introduction. Pinning hides the launcher; closing returns the same assistant to the hero on desktop. The launcher remains hidden while the hero assistant is visible.

Follow-up suggestions share the existing external-store assistant-ui runtime with the welcome screen. A portal mounts ThreadFollowupSuggestions below the DOM transcript; AuiIf and useAuiState read the active runtime suggestions, and ThreadPrimitive.Suggestion sends directly through the existing submit callback. The model generates prompts and ask/schedule_demo actions in the same invocation as the answer. A validated [[FOLLOWUPS]] JSON footer is removed from both streamed text (including partial marker chunks) and the final answer; suggestions travel separately in the final SSE event and are saved in the frontend turn. There is no fixed topic list or second model call. The client only validates/filter suggestions, respecting open drafts and refusals; explicit schedule_demo actions dispatch to the pinned preview regardless of their label wording. Invalid metadata produces no suggestions while preserving the answer.

The relevance guard adapts ArchiveLens’s structured relevance check to Lexcia’s scope. A separate non-streaming call returns a strict score, continue flag and short internal reason; routing applies the configured 5/10 threshold itself. It receives only two completed turns of bounded context and treats conversation text as data. Unrelated tasks and instruction/prompt extraction requests stop before retrieval and the answer model. Provider/schema failures fail closed. Guard stream events are excluded by the answer-node filter; only a safe notice is included in the final SSE payload. Stopped turns are not added to server history. Metadata-only logs avoid retaining raw questions or provider errors. Local and Vercel entry points both enable the gate.

The client renders `guardrail` final-event metadata using an adaptation of assistant-ui’s standalone GuardrailNotice, with Lexcia styling and actionable alternatives. A scope stop offers relevant product questions; a temporary check failure offers retry of the original question. These replace the normal answer body and have no ordinary follow-up suggestions. React roots are cleaned up when starting a new inquiry. This relevance gate adds a classification request before normal answers; the answer and its follow-up suggestions still share one answer-model call.
