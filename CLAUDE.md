## Development conventions

From the application root: `uv sync`; create `.env` from `.env.example` only if absent; then `cd website && npm ci`. Run `./scripts/dev.sh` from the root. Website: `http://127.0.0.1:5173`; backend: port 8767. Bearing Witness uses port 5174 and an external ArchiveLens backend on 8766.

Keep changes focused, follow surrounding Python/JavaScript/JSX conventions, and retain dependency lockfiles. Ground assistant answers in reviewed knowledge; preserve source links, input validation, session isolation and keyboard accessibility. Server conversation state is in memory, browser transcripts are local, and no durable account/history system exists. Update the relevant knowledge records and docs when behavior or product facts change; never invent capabilities or commercial claims.

Current assistant source behavior: the floating window opens near the draggable launcher, preferring the launcher below its bottom-left corner with 10 px spacing and viewport margins, and choosing another placement when necessary to fit. Opening, window-size changes, viewport changes and unpinning recalculate placement. Mobile retains its wide window; switching to the mobile layout unpins the panel. Desktop pinning docks it to the right in a native nonmodal dialog: the website reflows alongside it, stays clickable, and has no dimming or backdrop blur. Outside page clicks leave it open. Pinning and unpinning preserve the current conversation and do not replay the panel entrance or welcome animations, including while an answer is running. The right-edge divider supports pointer/keyboard resizing and caps width to keep about 400 px for the page when space allows. The launcher starts at 69.4% of viewport width and 73% of viewport height, matching the reference position in the right half of the hero, and remains draggable and viewport-constrained. Half a second after each page load, the assistant opens through the same floating modal path as a launcher click, without automatic pinning. Opening it manually cancels the pending automatic opening, so dismissing it does not trigger a second opening. Pointer resizing uses the current window dimensions and pointer deltas. The launcher is 58.19 × 58.19 px with a 26.45 × 26.45 px icon (15% larger than the earlier local version). Its background matches the earliest purple version: solid paper, white on hover or keyboard focus. It has a muted ink icon and a 1 px border with a continuous sage–ochre gradient with stronger color contrast against the paper and no blue segment, drawn directly in that same border and rotating once every five seconds. The color loop has broad, gradual transitions and no concentrated leading edge; the beam follows the rounded shape on hover and stays still when reduced motion is requested.

Before pushing relevant application changes, run `uv run pytest` and `(cd website && npm test && npm run build)`; for demo changes also run its `npm test` and `npm run build`. For documentation-only changes, verify links/paths and run `git diff --check`. Run commands in the actual application checkout, not an unrelated parent repository.

Conversation details follow assistant-ui's message/action-bar patterns while retaining the existing frame and SSE client: compact right-aligned user bubbles, unboxed Markdown answers, inline code and code-block copy controls, per-answer copying and helpful/unhelpful feedback, a waiting indicator, a growing composer, and a jump-to-latest control. The welcome screen adapts the actual assistant-ui website’s `AssistantWelcome` from `apps/docs/components/pages/docs/assistant/thread.tsx`: a staggered ochre-to-ink “Welcome to Lexcia!” greeting, the line “Ask Lexcia about the product, pricing, or your next idea.”, bottom-aligned starter rows, and subtle text/arrow hover states. It uses `AssistantRuntimeProvider`, `ThreadPrimitive.Root`, `AuiIf`, and `ThreadPrimitive.Suggestion send`, with `useExternalStoreRuntime` bridging the selected browser transcript and existing submit function. The composer, message bodies and outer frame stay under the existing DOM/SSE controller for this first integration step. Conversation history browsing is removed from the website; the + button still immediately starts a fresh chat. Existing browser transcript data is retained internally. The copied source’s MIT notice is retained in `website/public/licenses/assistant-ui.txt`. Message timestamps, day dividers and the separate Sources footer are currently omitted from the Lexcia website chat. Timestamp and source data remain in the saved turns and backend responses for later use. The website’s `TraceLine`/`ShimmerLabel` thinking treatment is adapted as a React-mounted > marker and softly shimmering “thinking…” label in muted ochre and ink; continuation uses “continuing…”. It clears on the first answer text, completion, error or cancellation. Progress appears only in the answer, leaving the composer clear. The composer has no Stop button; Send stays visible and disabled while a reply is running. Previously stopped or interrupted saved turns can offer Continue on the latest active turn; continuation appends to that message using the original question and saved answer ending, bounded by the existing 4,000-character request limit. New inquiries use fresh session IDs immediately. Copying strips internal source markers. Thumbs-down opens a reason/note dialog; feedback is stored only with the browser transcript, with no feedback API or shared analytics. The existing `@assistant-ui/react-generative-ui` renderer remains available for structured answers; the existing DOM/SSE controller remains the source of truth for conversation state.

## Git collaboration rules

1. Before starting, inspect status and remotes, then `git fetch origin` and `git pull --ff-only` on the working branch. If histories diverge, inspect and reconcile first. An empty repository has nothing to pull; fetch before its first commit.
2. Commit and push all completed changes with descriptive commit messages. Use `codex/` for new Codex branches; push the branch and communicate it. Never include another developer's unfinished work.
3. Never force-push, rewrite shared history or overwrite another developer's changes.
4. If a push is rejected, fetch, inspect incoming changes and reconcile before retrying; rerun relevant checks after reconciliation.
5. For conflicts, inspect both versions, their common ancestor and commit history. Resolve automatically only when both changes can safely coexist.
6. If changes contradict each other or intended behavior is unclear, stop and ask the developer. Never arbitrarily select one version or discard work.
7. Run relevant tests before pushing, review the staged diff, and never commit secrets or local `.env` files.
